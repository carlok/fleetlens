# Master Prompt: Build an Ansible-in-Podman VM Health Checker with Python Reporting and Email Notifications

You are an expert DevOps/SRE engineer, Python project maintainer, and Ansible automation specialist.

Design and implement a complete, clean, production-lean open-source style project for checking a small fleet of Linux virtual machines over SSH.

The project must use:

* **Ansible as the deterministic collector**
* **Podman as the execution wrapper**
* **Python as the report renderer and notification layer**
* **Email notifications for reporting**
* **YAML/INI configuration files**
* **Tests, coverage, linting, README, docs, CI, and examples**

The user already has:

* A few Linux virtual machines.
* SSH access to each VM.
* Sudo rights on each VM.
* A list of target machines.
* An existing cron-based HTTP/HTTPS checker.
* A preference for deterministic infrastructure tooling instead of autonomous agents.

The goal is to build a small but robust VM health checker that logs into each machine, collects operational facts, determines whether machines need apt updates or attention, generates JSON and Markdown reports, and optionally sends an email notification.

The tool must be suitable for cron or systemd timer execution.

---

## Core architecture

Implement the architecture as:

```text
cron/systemd timer
        |
        v
Podman container
        |
        v
Ansible collector
        |
        v
raw structured collection output
        |
        v
Python renderer
        |
        +--> JSON report
        +--> Markdown report
        +--> terminal summary
        +--> optional email notification
```

Ansible should collect facts and run safe checks.

Python should:

* Normalize Ansible output.
* Classify warnings and critical issues.
* Render reports.
* Send email notifications.
* Provide testable parsing/classification logic.

Do not use Ansible templates for the final report except for very minor helper output if useful. The main report generation must be done by Python.

## Safety rules

The default mode must be read-only or nearly read-only.

Allowed by default:

* Ansible fact gathering.
* Reading OS metadata.
* Running `uname`.
* Running `uptime`.
* Running `free`.
* Running `df`.
* Running `systemctl --failed`.
* Running `apt list --upgradable`.
* Running `apt-get -s upgrade`.
* Checking `/var/run/reboot-required`.
* Running `journalctl` only if enabled.
* Running `needrestart` or `checkrestart` only if installed and enabled.

Configurable:

* `apt-get update` to refresh package metadata.

Disallowed by default:

* `apt upgrade`.
* `apt full-upgrade`.
* `apt autoremove`.
* Restarting services.
* Rebooting machines.
* Cleaning disks.
* Modifying application state.
* Running commands generated by an LLM.

If remediation is discussed, put it only in the roadmap or architecture notes. Do not implement active remediation in version 1.

## Report classification requirements

Python must classify global status as:

```text
OK
WARNING
CRITICAL
UNKNOWN
```

Suggested rules:

* `CRITICAL` if any host is unreachable.
* `CRITICAL` if disk usage exceeds critical threshold.
* `CRITICAL` if sudo failed and checks could not run.
* `WARNING` if apt updates are available.
* `WARNING` if reboot is required.
* `WARNING` if systemd failed units exist.
* `WARNING` if journal errors exist and journal check is enabled.
* `OK` if no issues are detected.
* `UNKNOWN` if the report cannot be parsed.
